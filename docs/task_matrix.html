Agent Augmentation Architectures for LLM Coding Agents

This interactive matrix reports an empirical study of whether augmenting a large-language-model coding agent with additional structure — richer prompts, context-gathering sub-agents, self-verification, and multi-agent collaboration — improves its ability to solve real terminal tasks. Fourteen agent architectures are evaluated on the same task suite across several models spanning a wide capability range.

Research question. Does agent augmentation actually help — and does its benefit depend on how strong the underlying model already is? Every architecture is compared against that model’s own plain baseline, on identical tasks under an identical budget (single run, temperature 0, 60 steps / 30-minute wall-clock).

The 14 architectures (grouped G1–G4)

  • G1 — Single-agent variants: Baseline (plain ReAct agent), Prompt (enhanced system prompt), Temp (raised sampling temperature).
  • G2 — Context augmentation: Explorer (a scout gathers context first), Planner (explores then decomposes the task into sub-tasks), Analyst (explorer + planner-style analysis but without task decomposition), Monitor (a supervisor injects course-corrections mid-run).
  • G3 — Self-verification: Instruction & Reflexion (a verifier inspects the attempt and, if it deems changes are needed, applies the fixes itself), Judge (an independent verifier approves or rejects and sends the task back to the original agent to retry), Gate (a checkpoint intercepts before submission).
  • G4 — Multi-agent: Cooperation & Debate (two agents collaborate / argue toward a solution), Orchestra (an orchestrator routes the work to specialist sub-agents and integrates their outputs).

Models & tasks

Models span a capability ladder: Qwen2.5-Coder (7B / 14B / 32B), Qwen2.5-72B, Devstral-Small-24B, Llama-3.1-70B, and Gemini 3.1 Flash-Lite. Open models are served locally (4-bit quantized); Gemini via its hosted API. Model tabs are labelled by parameter count (Qwen7 / Qwen14 / Qwen32 / Qwen72, Devstral24, Llama70, Gemini).

Heterogeneous “Gemini supervisor” tracks. Three extra tabs — Gemini-Qwen32b, Gemini-Devstral24, Gemini-Llama70 — run a two-model agent: Gemini-3.1-Flash-Lite acts as the supervisor (it plans, inspects, and verifies — the Explorer / Planner / Analyst / Monitor / Judge / Orchestrator roles) while the named weaker model is the worker that actually executes the terminal commands. Only the 6 architectures with a separable supervisor role apply (the other 8 have no distinct supervisor to swap).

Tasks are the “easy” subset of TerminalBench (62 tasks) — standard coding, data, and system-administration problems that must be solved from a terminal, each graded by an automated test suite. Two tasks of the original 64 are excluded as infeasible on our setup (multi-gigabyte Docker images / GPU-only builds that don’t fit the harness), leaving 62. All 62 are ranked together (there is no separate “core” vs “extra” grouping in the display).

Preliminary observations

Early results (single-run, indicative rather than definitive) suggest that the value of augmentation scales inversely with base-model strength:

Llama-3.1-70B (4-bit)weak baseline— nearly every architecture improves on it.
Devstral-24Bmid baseline— mixed: multi-agent (cooperation / debate) & verification (judge) help most; context-gathering tends to hurt.
Qwen2.5-Coder-32Bstrong baseline— no architecture beats it; scaffolding is dead weight.
Gemini-3.1-Flash-Litestrongest baseline— only self-verification (Reflexion / Judge / Gate) still pays; context-gathering and multi-agent orchestration actively hurt.

Intuition: augmentation rescues a weak-but-revisable first attempt, but adds little to a model already near its ceiling — and at the very top, only lightweight self-verification survives while heavier orchestration becomes overhead. The architectures are also complementary — different ones solve different tasks — so a best-per-task oracle would exceed any single architecture. The Gemini-supervisor tracks test the flip side: can a strong supervisor raise a weaker worker? (runs in progress.)

How to read the matrix

  • The filter panel at the top drives everything. Pick a single Model to see all of its architectures (14 for the standalone models; 6 for the Gemini-supervisor tabs). Click Overview any time to return here.
  • All chip rows are multi-select — click several Models and/or Architectures (or an All chip to reset) to build a custom cross-cut. Selecting one architecture across several models, for example, lines them up side by side for direct comparison. Tasks chips filter the rows by category.
  • Rows are tasks in one global order, easiest → hardest by how many model×architecture cells solved them (live on every build). Thin vertical lines separate architecture groups (G1–G4), so columns within a band are the most directly comparable.
  • Columns are architectures. The last two, Solved and Best%, summarise how many configurations solved a task and the best sub-test pass rate. The Sub-tests toggle (top-right) overlays per-cell sub-test counts and the green/red comparison dots.
  • On a single-model view, bright green cells mark a gain over that model’s own baseline, red a regression; the small dots flag partial (sub-test) progress even when a task was not fully solved.

Boundary probe — is there any signal beyond “easy”?

The grid above is restricted to TerminalBench’s easy band. To turn the “these models fail almost entirely on harder tasks” assumption into a measurement, a pre-registered boundary probe ran four models spanning the capability range (Llama-70B, Devstral-24B, Qwen-32B, Gemini) on 20 medium + 20 hard tasks, g1_baseline only. It is a separate boundary measurement — it lives outside the easy grid and never enters any solve-rate shown above.
